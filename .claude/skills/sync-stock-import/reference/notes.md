# Stock import — reference notes

## Excel format (shop's "Stock Management.xlsx")
First worksheet, header row 1, columns:
`Name, Type, Brand, Color, Storage (GB), RAM (GB), Condition, Condition Rating (1-10),
Battery Health (%), PTA Status, IMEI / Serial, Quantity, Cost Price (PKR),
Selling Price (PKR), Notes`

Each row = a "line" of `Quantity` identical units. Empty rows are ignored.

## Data model (how variants/products work)
- `brands → models → variants → products`.
- A **variant** = unique `(model_id, storage_gb, pta_status, condition)`. Color is NOT in
  the variant key — it's per `product`, aggregated into `variants.available_colors`.
- `variants.selling_price` is single-valued; `stock_count`, `avg_cost_price`,
  `available_colors`, `is_active` are auto-computed by a trigger from child products.
- **Slug** is auto-generated by the `trg_variants_auto_slug` BEFORE-INSERT trigger from
  `brand + model + storage + condition + pta`. Insert variants with `slug` NULL and the
  DB fills it. Store **brand-stripped** model names (e.g. `Pixel 8 Pro`, not
  `Google Pixel 8 Pro`) or the slug double-brands (`google-google-...`).
- `variants.pta_status` is **TEXT**; `products.pta_status` is the **enum `pta_status`** —
  always cast `::pta_status` when inserting into products (the generated SQL does this).

## Shop-specific cleanup (applied in stock_import.py `canon_model`)
- `CP` / `cp` suffix in a model name = the unit is **Non-PTA**; the suffix is dropped.
- A trailing `512` in the name is a redundant storage tag → dropped.
- `pixel 7 a` → `pixel 7a` (a-series); `oneplus13t` → `OnePlus 13T` → stored as `13T`.
- Final display name comes from GSMArena (`fetch-specs` → `modelName`, brand-stripped).

## Normalization (GSMArena)
- `prepare` calls the backend `/api/products/fetch-specs` per model → canonical name,
  colors, storage, RAM. Generic Excel colors are mapped to marketing colors
  (black→Obsidian, blue→Bay/Sea/Indigo, etc.) via `COLOR_KW` + exact match; ambiguous
  ones are flagged UNCERTAIN for human override.
- RAM is taken from GSMArena (single value auto-applied; the Excel RAM is unreliable —
  e.g. it had Pixel 10 as 16GB when it's 12GB).

## Conflicts that are skipped
Variant groups where multiple Excel rows share `(model,storage,pta,condition)` but have
**different selling prices** are set aside (a variant has one price). `overview` lists
them; fix the sheet to include them.

## Known app bugs found while building this (context)
- `add_stock` RPC inserted TEXT `pta_status` into the enum column without a cast → every
  "Add stock to existing variant" call 400'd. Fixed in migration
  `20260523000001_fix_add_stock_pta_cast.sql`. Even fixed, `add_stock` does not set
  `ram_gb`/`condition_rating`/`battery_health`/`imei`. → This skill loads via SQL, which
  sets all fields, instead of the UI.
- The inventory "Add Product" form cannot create a new model (typed names → orphan
  products with no variant/slug). Models are created on `/admin/models` (GSMArena-gated).

## Environment gotchas
- Port **3001** is often held by an unrelated "NRPU Admin" app on this machine — run the
  shop backend on another port (e.g. 3099) and set `STOCK_API` accordingly.
- GSMArena search/fetch **rate-limits** rapid bulk calls; `prepare` sleeps 0.4s between
  models. `fetch-specs` is cached server-side, so re-runs are fast.
- Never `supabase db reset` and never push migrations to prod (see project CLAUDE.md).
