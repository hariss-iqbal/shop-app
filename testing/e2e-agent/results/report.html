7Production Hazard Spotlight: Rapid Double-Submit Guard Fix

The Problem

Angular's [disabled]="saving()" template binding is asynchronous — it schedules a DOM attribute update on the next change-detection cycle. A user who double-clicks a Save button faster than that cycle fires will have both clicks reach the submit handler. Both fire await this.service.create(...) concurrently, and two identical rows are inserted into the database. This is a production data-integrity vulnerability.

Before / After

// Before (vulnerable) — 6 forms had this pattern
async onSubmit() {
  if (this.form.invalid) return;
  this.saving.set(true);  // [disabled] binding doesn't flush in same tick
  await this.service.create(...);
  this.saving.set(false);
}

// After (hardened) — synchronous guard blocks the second click
async onSubmit() {
  if (this.saving()) return;  // <-- synchronous guard, evaluated immediately
  if (this.form.invalid) return;
  this.saving.set(true);
  await this.service.create(...);
  this.saving.set(false);
}

Verification: rapid-double-submit-supplier test confirmed that after the fix, rapid double-clicking produces exactly 1 row with the unique RUN-suffix. matchingThisRun=1 on all 3 regression playbooks (supplier-create, brand-create, sales-create-add-product) in Iter 9.

Why [disabled] alone is insufficient: Angular signals (signal()) are synchronous reads but [disabled]="saving()" is a template binding that only updates the DOM on the next change-detection cycle. The sequence on a rapid double-click: click-1 fires handler, saving.set(true) runs, change detection is scheduled, click-2 fires handler (saving is true in memory but DOM button not yet disabled), both reach await create(). The synchronous if (this.saving()) return guard short-circuits before any async work, making it immune to this race.
